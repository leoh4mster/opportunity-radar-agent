# Opportunity Radar Agent 面试讲解指南

这份文档用于帮助项目作者在实习或校招面试中，用产品、工程和 AI 三个角度讲清楚项目。

## 30 秒版本

我做了一个面向大学生和求职者的机会雷达 Agent。它把公众号文章里的实习、竞赛和科研信息抽取成结构化机会，再根据用户画像、截止时间、收益成本和历史反馈进行个性化排序。用户可以继续创建待办、日历提醒和推进计划，系统也会从长期行为中形成成长记忆。项目采用 FastAPI、Streamlit、SQLAlchemy 和 SQLite，并设计了无 API Key 的本地降级路径，因此可以稳定演示完整主流程。

## 3 分钟讲解结构

### 1. 问题

- 公众号机会信息多，但分散且格式不统一。
- 用户无法快速判断“是否适合我”，也容易错过截止日期。
- 收藏文章不等于真正行动，缺少后续跟进和复盘。

### 2. 解决方案

把一次性的文章阅读变成持续决策链路：抽取信息、个性化排序、创建行动、收集反馈、更新长期记忆。

### 3. 技术实现

- Streamlit 负责快速构建可交互产品原型。
- FastAPI 提供稳定、可测试的业务 API。
- SQLAlchemy 将文章、机会、推荐、状态和行为持久化。
- Tool Registry 把核验、补全、待办和日历封装为可扩展 Agent 工具。
- DeepSeek 负责适合生成式模型的任务；本地规则负责稳定性和离线演示。

### 4. 最值得讲的设计选择

**为什么不是所有功能都调用大模型？**

大模型适合语义理解和自然语言生成，但数据库状态变更、截止日期判断、去重和评分边界需要确定性。项目将两者分开，并在远程模型不可用时自动回退到本地规则。

**为什么要保存行为事件？**

静态画像只能表达用户“说自己喜欢什么”，行为事件能反映用户“实际做了什么”。推荐反馈、创建待办和已申请属于不同强度的信号，可以用于后续成长记忆和推荐调整。

**Agent 体现在哪里？**

Agent 不只是聊天框。它围绕机会读取上下文、选择并执行工具、改变机会状态、记录结果，再把结果用于下一步决策。工具调用有明确输入输出，也会写入日志，便于追踪。

## 推荐现场演示

1. 从“总览”说明系统当前状态以及无 Key 降级能力。
2. 修改一个用户画像，加入具体目标和技能。
3. 导入文章并处理，展示机会库字段。
4. 刷新推荐，解释为什么某条机会排在前面。
5. 查看原文，创建待办和日历提醒。
6. 提交“有用/不感兴趣”反馈，说明反馈闭环。

## 常见追问

### 推荐分数怎么计算？

基础分数以相关性和收益为主，同时考虑紧迫度、成本、地点时间偏好、信息可信度以及用户反馈。当前权重是工程规则，后续可以通过离线评测和真实点击数据学习权重。

### 如何避免模型编造截止日期？

日期和报名入口属于高风险字段。没有明确信息时系统保留“待确认”，日历服务也不会强行创建提醒；联网结论必须附来源，基础模式则提示用户回到原文核验。

### 当前最大的局限是什么？

- 示例数据规模有限，推荐效果还没有真实用户评测。
- 公众号自动采集仍是桌面实验模块，稳定性受客户端界面影响。
- 单机 SQLite 适合演示，但多用户部署需要 PostgreSQL、登录和权限隔离。
- 成长记忆目前依赖行为规则与大模型总结，还需要防止短期行为被过度解释。

### 下一步如何产品化？

先建立推荐评测集和可观测指标，再整理采集模块、加入数据库迁移和结构化日志，最后补用户系统与云端部署。顺序上优先保证结果可评估，而不是继续增加无法验证的 Agent 功能。

## 可以量化的指标

后续可围绕这些指标迭代：

- 抽取准确率：机会字段与人工标注的一致率。
- 推荐命中率：Top-K 推荐中被标记有用或申请的比例。
- 截止日期覆盖率：有明确且核验日期的机会比例。
- 行动转化率：推荐到待办、日历或申请的转化。
- 降级成功率：外部模型不可用时基础主流程仍能完成的比例。
