# 持久化任务与异步接口

更新：2026-10-02。适用于 `0004_durable_jobs` 及之后的代码。

## 执行规则

抽取、推荐刷新、推进分析和联网核验统一进入 SQLite `durable_jobs`。应用生命周期启动一个串行 worker，每秒检查任务；每次领取生成独立令牌，租约 60 秒，每 10 秒使用独立连接续租。保存阶段结果及业务结果前均验证令牌与租约，失去租约的执行者不能写回。

任务状态为 `queued / running / succeeded / failed`，与业务的 `waiting_confirmation / stopped / completed` 等状态分开。分析任务成功只意味着建议已生成，不意味着用户已确认或工具已执行。

每个任务最多执行两次。临时网络故障延迟 5 秒重试；进程中断导致租约过期后恢复。鉴权、余额、参数和结构错误直接失败。持久化任务内关闭模型网关重试和 JSON 修复请求；推荐候选、推进轮次、搜索结果都有检查点。手动重试创建关联的新任务，同一次失败记录上的重复重试请求返回同一个后继任务。

业务提交与任务成功在同一事务，外部调用期间不保持数据库会话。文章入库与任务创建先提交，抽取失败仍保留文章；推荐刷新失败保留旧推荐。输入快照在第一次执行前建立，恢复和最终提交时重新计算输入指纹；输入变化或被删除则失败，旧结果不覆盖新数据。

领取及写入使用 SQLite 短写事务，支持多个执行者竞争测试，但默认仍为本机单进程、单 worker。跨进程领取不代表外部调用恰好一次：响应收到但检查点尚未落库时崩溃，恢复可能重复调用和计费。两次执行也不是两次 HTTP 请求上限，一次推荐可能包含多个候选调用。

## 接口变更

以下提交操作返回 **HTTP 202**，不再等同于业务处理完成：

| 操作 | 返回数据 |
|---|---|
| `POST /articles/ingest-clean` | 原入库信息及 `job`；已处理的重复文章 `job=null` |
| `POST /pipeline/process` | `{jobs: [...]}`，每篇未处理文章一个任务；空列表表示无待处理文章 |
| `POST /recommendations/generate/{user_id}` | `{job: ...}` |
| `POST /recommendations/{user_id}/generate` | 同上；历史 `force` 参数保留接收，两个入口均提交刷新任务 |
| `POST /tools/opportunity-progress/{user_id}/{opportunity_id}/analyze` | `{success, task, job}`，保留业务任务数据 |
| `POST /tools/opportunity-progress/tasks/{task_id}/web-check` | `{success, web_check, job}` |
| `POST /tools/opportunity-progress/plans/{plan_id}/web-check` | 同上 |
| `POST /jobs/{id}/retry` | `{job: ...}`；非失败任务或输入已删除时返回 409 |

上传和路径导入仍只导入文章，点击处理按钮才提交抽取。采集接口自动提交抽取。相同类型和对象同时只存在一个活动任务，重复点击合并；推进分析已有待确认结果时继续返回已有结果。

- `GET /jobs/{id}`：查询执行状态。
- `GET /jobs?kind=...&object_id=...&user_id=...`：按业务对象过滤，倒序返回最近 500 条记录；列表不是完整历史导出。
- `kind` 为 `extraction / recommendation / analysis / web_check`；`object_id` 分别是文章 ID、画像 ID、推进分析任务 ID、联网核验记录 ID。
- `GET /recommendations/{user_id}` 继续读取当前推荐。推进任务、计划及核验结果原查询接口保留。

公开任务字段包括 `id / kind / object_id / user_id / status / attempts / retry_of / request_id / stage / completed / total / mode / error_code / error_message / created_at / updated_at / result / status_url`。`result` 只包含业务结果引用及数量，不返回输入快照、提示词、模型原文、检查点或租约令牌。

客户端每 2 秒轮询活动任务，结束后停止。Streamlit 重开页面从服务端恢复状态，刷新期间保留旧推荐；失败显示脱敏原因和请求 ID，支持手动重试。任务状态组件从主页面抽出，画像间使用独立控件状态。旧采集客户端已适配 202 并提供 `get_job_status`，外部旧调用方也需要更新，不能再直接读取同步处理计数。

无 Key 的抽取和推荐明确使用本地规则模式；配置 Key 后模型失败会进入失败/重试状态，不静默回退。推进分析需要模型；核验需要搜索服务及模型。未配置搜索或搜索无来源不视作核验成功。

## 迁移与运维

先停写并备份，升级后重启后端与前端。`0004` 只增加队列表，并把升级前遗留 `analyzing/searching` 业务记录标为“升级前中断，请手动重试”，不会自动重放私人历史内容。已有用户确认的结果保持不变。

队列快照和检查点可能含私人输入，随数据库和备份留在本机，不能提交到 Git。删除用户或文章会使相关活动任务失效并清除相应快照；文章变化会使推荐输入失效。`0004` 在无活动任务时可以降回 `0003`，但会丢弃任务历史，且不会恢复升级前的运行状态。实际回退优先恢复备份及对应旧代码；`0003` 本身仍不允许自动 downgrade。

查看 `GET /jobs` 的排队量、尝试次数、错误与请求 ID 排查问题。租约只在后端 worker 工作时恢复；后端完全停止时不会自行处理任务。尚未引入外部监控、权限体系、自动历史清理或多实例部署方案。
